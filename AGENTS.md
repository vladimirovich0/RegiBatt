# Rovnota Systems — обязательные правила разработки SaaS

Версия 2.1 · 16 сентября 2026

## 1. Обязательность и границы задачи

Ассистент обязан руководствоваться этим файлом при разработке Rovnota Systems. Перед изменениями читать актуальные AGENTS.md, PROJECT_PLAN.md и BRANDBOOK.md, проверять реальные файлы проекта и сохранять пользовательские изменения.

- AGENTS.md определяет архитектуру, стек, организацию кода и проверки.
- PROJECT_PLAN.md определяет этапы продукта, их приоритет, границы и критерии завершения.
- BRANDBOOK.md определяет утверждённый внешний вид. Подтверждённые пользователем решения по стилю фиксировать там в той же задаче.
- Новое прямое указание пользователя имеет приоритет над прежним проектным решением. Обновлять устаревшее правило, не оставлять противоречащие друг другу инструкции.
- Эта версия заменяет прежнюю архитектуру «только статический HTML/CSS/JS» целевой архитектурой SaaS.
- Сейчас в корне остаётся статический прототип, а в `battery passport demo/` — отдельное локальное демо сценария паспорта батареи. Ни один из этих артефактов сам по себе не подтверждает запуск продукта или завершение этапа 1.
- Каталог сайт/ не считать автоматически рабочей версией; до изменений выяснить его назначение.
- При задаче только на документацию не менять код, не устанавливать пакеты и не создавать инфраструктуру.
- Файлы и папки ниже создавать по необходимости, а не все заранее.

## 2. Подтверждённый продукт и этапы

Rovnota Systems — B2B SaaS для работы с данными и документами батарей. Полный продуктовый план и критерии перехода между этапами находятся в `PROJECT_PLAN.md`.

**Этап 1 — Rovnota Data Readiness.** Единственный активный продуктовый приоритет: запустить AI-сервис, который принимает документы по батарее, структурирует относящиеся к паспорту данные, сохраняет их происхождение и показывает собранные поля, пропуски, конфликты и значения, требующие ручной проверки.

В объём первого этапа входят только возможности, необходимые для работающего сквозного сценария и безопасного запуска: доступ пользователей, изолированные рабочие данные, приём документов, AI-извлечение и нормализация, карта готовности, ручная проверка и выдача согласованного структурированного результата. Конкретные форматы экспорта и API выпускать по необходимости этого сценария, а не как самостоятельное расширение продукта.

Этап 1 не считается выполненным по наличию макетов, локального демо, кода или успешной сборки. Он завершён только после развёртывания доступной предназначенным пользователям рабочей версии и успешной проверки основного сквозного сценария. До этого этап остаётся активным, если пользователь явно не изменил план.

**Этап 2 — Rovnota Document Workspace.** Развитие проекта дополнительными инструментами для работы с документами. Детальный объём определяется после запуска этапа 1. Не начинать функции этапа 2 раньше, кроме необходимой общей основы или прямого изменения плана пользователем.

Бюджет хостинга ограничен, точная сумма и ожидаемая нагрузка пока не определены. Проектировать низкую постоянную стоимость, ограниченное потребление памяти и предсказуемые расходы на документы и трафик. Не обещать производительность или стоимость без измерений.

Описание будущих возможностей в брендбуке не означает, что они уже реализованы. Проверка полноты данных и CSV/JSON-экспорт сами по себе не являются юридической сертификацией или регистрацией паспорта.

## 3. Целевой стек

| Слой | Выбор | Назначение |
|---|---|---|
| Язык приложения | TypeScript, strict | Типизированный клиентский и серверный код |
| Web-фреймворк | Next.js, App Router | Публичные страницы, кабинет и HTTP API в одном приложении |
| Интерфейс | React, Server Components по умолчанию | Серверная подготовка интерфейса, клиентский JS только для взаимодействий |
| Серверная среда | Node.js, актуальная Active LTS | Переносимый серверный runtime |
| Стили | CSS Modules + общие CSS-переменные | Изоляция компонентов и единый бренд без runtime CSS-in-JS |
| База данных | PostgreSQL | Пользователи, организации, батареи, документы, версии и аудит |
| Доступ к БД | Drizzle ORM + pg | Типизированные запросы, пул соединений и проверяемые SQL-миграции |
| Валидация | Zod | Проверка входных данных и схемы контрактов |
| Авторизация | Better Auth + PostgreSQL/Drizzle | Сессии, вход, восстановление и подтверждение почты |
| Файлы | Приватное S3-совместимое хранилище | Документы отдельно от приложения и БД |
| Локализация | next-intl | Русский и английский, серверные переводы и локализованные URL |
| API интеграций | REST JSON + OpenAPI | Версионированный, документируемый HTTP-контракт |
| Зависимости | pnpm, один lockfile | Воспроизводимая установка |
| Проверки | ESLint, Prettier, TypeScript, Vitest, Playwright | Статический анализ, бизнес-логика, интеграции и сценарии браузера |
| Развёртывание | Docker, Next standalone, reverse proxy Caddy | Самостоятельный хостинг с HTTPS и возможностью переноса |

Это проектный выбор под требования Rovnota Systems, а не утверждение, что один стек быстрее всех остальных при любой нагрузке.

CSS остаётся языком оформления и в современном React-приложении. JSX/TSX описывает структуру и поведение компонента; стили находятся рядом в отдельном .module.css. HTML, CSS и JavaScript остаются результатом работы web-приложения в браузере.

Не добавлять параллельно Vite, отдельный Express/NestJS backend, второй ORM, Redux, GraphQL, Redis, Kubernetes или микросервисы без измеримой потребности. React Hook Form, TanStack Table/Query и headless-компоненты подключать только при сложности конкретной формы, таблицы или взаимодействия; не ставить весь набор автоматически.

## 4. Политика актуальности версий

Ориентиры, проверенные по официальным источникам на дату документа: Next.js 16.x, React 19.2, Node.js 24 LTS, PostgreSQL 18. Это семейства версий, а не инструкция навечно закрепить сегодняшние patch-релизы.

- Перед первым scaffold проверить свежие стабильные версии и совместимость Next.js, React, TypeScript, Node.js, Better Auth, Drizzle и адаптеров.
- Для production выбирать стабильные поддерживаемые релизы с актуальными исправлениями безопасности. Не использовать canary, beta, RC и experimental-флаги по умолчанию.
- Более новый Node Current не заменяет автоматически Active LTS.
- Точную версию Node записывать в файл версии runtime и Docker-образ; pnpm — в packageManager; зависимости — в package.json и pnpm-lock.yaml.
- В CI применять frozen-lockfile. Не смешивать pnpm-lock.yaml, package-lock.json и yarn.lock.
- Проверять обновления регулярно; исправления безопасности оценивать оперативно, major-обновления проводить отдельной проверяемой задачей.
- Проверять release notes и peer dependencies. Не запускать бесконтрольное обновление всех пакетов и force-исправления аудита.
- Контролировать install scripts зависимостей; не разрешать произвольные scripts всем пакетам ради успешной установки.
- README должен отражать реально установленные версии и команды. Не выдавать целевой стек за уже работающий.

## 5. Архитектура приложения

Начальная архитектура — модульный монолит: один репозиторий и одно Next.js-приложение, внутри которого отделены предметные модули.

Поток запроса:
UI / REST endpoint → серверный контекст пользователя и компании → проверка доступа и схема входа → сервис предметной области → репозиторий / хранилище.

- Публичный сайт и кабинет разделять route groups и layouts.
- Компоненты UI не обращаются напрямую к БД и не содержат правил доступа.
- Route Handlers и Server Actions — тонкие адаптеры. Они вызывают одни и те же сервисы, чтобы UI и API применяли одинаковые бизнес-правила.
- Server Components вызывают серверные сервисы напрямую, без HTTP-запроса к собственному API.
- Server Actions использовать для внутренних действий UI; внешнее API строить на Route Handlers.
- Сервисы не зависят от React, Request/Response и cookies. Передавать проверенный контекст явно.
- Серверные подключения, секреты и код хранилища помечать server-only и не импортировать в клиентские модули.
- Не создавать универсальный repository framework и сложную систему событий до реальной потребности.
- Долгие экспорты и ресурсоёмкую OCR/AI-обработку выполнять отдельным worker-процессом, переиспользующим серверные модули, когда синхронная обработка перестаёт укладываться в безопасные лимиты HTTP-запроса.

## 7. UI, CSS и бренд

- Общая база одна: tokens.css с палитрой и смысловыми значениями; globals.css с reset, базовой типографикой и общими правилами доступности. Подключать через корневой layout.
- Стили компонента находятся в его .module.css. Layout-компоненты также имеют собственные модули; не дублировать шапку, логотип и кнопки по страницам.
- Цвета брать из брендбука через переменные назначения: фон, поверхность, текст, акцент, граница, фокус. Для тем переопределять переменные, а не копировать стили.
- Inter — основной шрифт; Montserrat 800 — название Rovnota; Manrope 700 — утверждённые надзаголовки.
- Шрифты размещать локально в WOFF2 с лицензиями и next/font/local. Загружать только нужные веса и наборы символов; сохранить кириллицу и латиницу.
- Единицы и размеры — по брендбуку: rem для текста и отступов, px для тонких границ и точных размеров знака, %, fr, min/max/clamp для адаптивности.
- Не задавать runtime-стили в JSX без необходимости. Допустимы динамические CSS-переменные.
- Не использовать !important и длинные глобальные селекторы для обычной стилизации.
- Фокус, контраст и клавиатурное управление проверять в обеих темах. Учитывать reduced motion, масштабирование текста и экран от 320 px.
- Интерактивным элементам давать удобную область нажатия около 44 × 44 CSS px; размер иконки может быть меньше.
- Публичные тексты показывают реализованные возможности. Не публиковать обещания работающего OCR или гарантированной регуляторной сертификации до основания для таких утверждений.

## 8. Рендеринг, состояние и локализация

- Публичные страницы предварительно генерировать или кэшировать, когда содержание позволяет.
- Кабинет и пользовательские данные получать на сервере с проверкой доступа; не помещать персональные ответы в публичный CDN-кэш.
- Не добавлять use client в общий layout ради одного переключателя. Клиентские границы делать небольшими.
- Фильтры, сортировку и пагинацию хранить в URL, временное UI-состояние — локально в компоненте.
- TanStack Query добавлять при необходимости клиентского обновления данных; не дублировать им без причины серверную загрузку.
- Кэшировать только с явными правилами срока, инвалидации и изоляции компании. Ключи включают tenant и значимые параметры; сам ключ не заменяет авторизацию.
- Локализованные страницы после миграции: /ru/... и /en/.... Русский — default, выбор пользователя сохраняется; явный URL определяет язык текущей страницы.
- API /api/v1 не включать в языковые redirect-правила.
- Сообщения и подписи хранить в messages/ru.json и messages/en.json. Не разбрасывать тернарные переводы по компонентам.
- Переводить metadata, ошибки, aria-label, пустые состояния и письма. Числа и даты форматировать через Intl с явной локалью.
- Обновлять lang, canonical и hreflang для публичных страниц. Кабинет исключать из индексации, но не считать noindex защитой доступа.
- Тёмная тема остаётся default. При миграции учитывать существующие ключи localStorage; хранение темы и языка не должно вызывать сбой при запрете storage или hydration mismatch.
- Авторизационные токены не хранить в localStorage.

## 9. Данные компаний и авторизация

- Организация — tenant. Пользователь может состоять в нескольких организациях; членство и роль проверяются на сервере.
- Базовые роли: owner, admin, editor, viewer. Матрицу разрешений описать до реализации; по умолчанию доступ запрещён.
- Все бизнес-сущности компании имеют organization_id. Tenant получать из проверенного членства/сессии/API-ключа, не доверять идентификатору из формы.
- Каждый доступ, включая списки, отдельные объекты, файлы, экспорт и фоновые задания, ограничивать organization_id.
- SQL-ограничения и составные внешние ключи должны предотвращать связи объектов разных компаний. RLS допустим как дополнительный слой с транзакционным tenant-контекстом; не включать его формально без тестов пула соединений.
- Better Auth отвечает за сессии и пароли; не писать собственную криптографию и восстановление паролей.
- Cookies сессии: HttpOnly, Secure в production, подходящий SameSite. Проверять origin/CSRF для действий через cookies.
- Проверка доступа обязательна внутри сервисов/обработчиков; скрытая кнопка, layout или proxy не являются достаточной защитой.
- Использовать подтверждение почты, ограничение попыток входа, отзыв сессий и одноразовые истекающие ссылки восстановления.
- Секреты только на сервере, без NEXT_PUBLIC_. .env.example содержит имена и безопасные примеры; .env и реальные ключи не коммитить.
- Логировать значимые изменения с actor, organization, объектом и временем; не записывать пароли, токены и содержимое документов.

## 10. База данных и миграции

- PostgreSQL хранит структурированные данные и метаданные файлов. Документы и base64 не помещать в строки БД.
- До реализации определить сущности: users, organizations, memberships, batteries, documents, версии данных, export jobs, API keys, audit events. Auth-таблицы согласовать со схемой библиотеки.
- Типизированные поля использовать для известных атрибутов; JSONB — для действительно переменных частей, не вместо всей модели.
- Хранить источник данных, версию схемы и историю значимых изменений. Отсутствующее значение не превращать в ноль или выдуманный факт.
- Точные измерения и финансовые значения при их появлении хранить подходящим numeric, время — timestamptz/UTC.
- Параметризовать запросы, ограничивать выбираемые столбцы, исключать N+1.
- Пагинация обязательна для растущих списков; стартовый размер 25, максимум 100. Для больших наборов — курсоры со стабильной сортировкой.
- Индексы выбирать по запросам, прежде всего tenant + фильтр/сортировка. Проверять планы дорогих запросов.
- Один ограниченный пул соединений на процесс, с таймаутами. Сумма пулов web и worker должна оставлять запас PostgreSQL.
- Миграции генерировать и ревьюить как SQL, хранить в Git. Не выполнять schema push, reset или разрушительные миграции production автоматически.
- Миграции выполнять отдельным шагом релиза с блокировкой от параллельного запуска. Перед опасными изменениями — backup и проверенный путь восстановления.
- Изменения схемы выполнять совместимыми этапами expand/contract, чтобы rollback приложения оставался возможным.

## 11. Документы и экспорт

- Пользовательские документы хранятся в private bucket вне public/ и контейнера приложения.
- Выдавать короткоживущие подписанные ссылки только после проверки доступа; объектные ключи генерировать сервером с привязкой к компании.
- Ограничивать размер, количество файлов, типы и общий объём компании. Проверять содержимое/MIME, а не только расширение.
- Прямая загрузка в S3 должна завершаться серверной проверкой объекта и квоты; подпись URL не означает успешную валидацию.
- До проверки файл имеет статус quarantine. Для недоверенных файлов предусмотреть антивирусную проверку; ошибки проверки не переводят файл в ready.
- Пользовательские HTML/SVG и другие активные форматы не отображать как доверенный код. Скачивание — attachment; безопасный preview — отдельный ограниченный механизм.
- Удаление и очистку незавершённых загрузок согласовывать между БД и хранилищем, делать повторяемыми. Исходники сохранять по определённой политике хранения.
- CSV/JSON выдаётся только по правам пользователя и компании. Выбор столбцов — явный allowlist, без внутренних секретов.
- JSON имеет версию схемы, документированные единицы и стабильные поля; структура не зависит от RU/EN интерфейса.
- CSV: UTF-8, документированные заголовки и разделитель, корректное экранирование кавычек/переносов. Нейтрализовать формулы в пользовательских текстовых ячейках для табличных редакторов; JSON сохраняет исходные данные.
- Небольшие ограниченные экспорты выполнять синхронно с таймаутом. Большие — курсором/пакетами и streaming с backpressure либо через worker.
- Не собирать всю большую выгрузку в RAM. Фиксировать версию/снимок данных для согласованности результата.
- Для фонового экспорта: статус, прогресс при наличии, повторная попытка, срок хранения результата, приватная ссылка скачивания.

## 12. Публичное API

- REST endpoints под /api/v1, независимые от локали и структуры компонентов.
- OpenAPI — обязательный контракт: схемы запросов/ответов, авторизация, примеры, пагинация, ошибки и лимиты. Совместимую стабильную версию спецификации закрепить вместе с генератором.
- Zod-схемы согласовывать с OpenAPI автоматически или контрактными тестами; не поддерживать вручную расходящиеся описания.
- Машинный доступ — отдельные API-ключи компании со scopes, сроком действия, отзывом и ротацией. Секрет показывать один раз; сохранять хеш, идентификатор и метаданные.
- Сессии браузера и машинные ключи имеют разный жизненный цикл, но используют общую авторизацию предметной области.
- Вход валидировать на сервере, лимитировать body, строки, страницы и длительность операций.
- Rate limits: по IP для анонимных запросов, по ключу/компании для API; 429 и Retry-After. Для нескольких процессов счётчики общие, не локальный Map.
- Ответы ошибок имеют стабильный машинный code, понятное сообщение и requestId, без SQL и stack trace.
- Для создающих дорогие ресурсы запросов поддерживать idempotency key с областью company + operation, хешем payload и ограниченным сроком хранения.
- Долгие экспорты возвращают 202 и идентификатор задания; клиент проверяет статус с backoff, без частого бесконечного polling.
- Использовать корректные HTTP-статусы, сортировку allowlist, UTC/ISO-даты и документированные числовые форматы.
- Bearer-ключи не требуют wildcard CORS. Разрешённые origins определять по сценариям; cookie-запросы защищать отдельно.
- Изменения v1 сохраняют совместимость. Breaking changes — новая major-версия API с документированным переходом.
- Webhooks, OAuth и SDK добавлять по отдельной необходимости, не проектировать несколько способов интеграции заранее.

## 13. Хостинг и контроль затрат

Стартовая схема: один небольшой Linux VPS с Docker Compose (web, Caddy, PostgreSQL) плюс внешнее private S3-хранилище и отдельное место резервных копий. Это экономичный проектный вариант, который требует обслуживания и имеет единую точку отказа.

- Конкретного провайдера, тариф и регион пока не выбрали. Перед заказом сравнить полную стоимость: compute, storage, egress, backups, почта и обслуживание.
- Регион ЕС предпочтителен с учётом аудитории; требование обязательной резидентности данных, включая backups и обработчиков, уточнить до загрузки реальных документов.
- Managed PostgreSQL допустим, если бюджет покрывает снижение операционных рисков. Не вводить обязательную зависимость от Vercel или другого единственного провайдера.
- Next.js собирать в CI, разворачивать standalone production-образ; не запускать dev server и тяжёлую сборку на малом production VPS.
- Web запускается непривилегированным пользователем; HTTPS завершается на Caddy. БД доступна только по приватной сети.
- Для контейнеров задавать лимиты ресурсов, healthchecks, restart policy и ограничение логов. Документы не хранить в writable layer контейнера.
- Миграции и backups не запускать при каждом HTTP-запросе или старте реплики.
- Делать резервные копии БД вне VPS, проверять восстановление; для файлов предусмотреть согласованное резервирование/версионирование и retention.
- Перед production зафиксировать RPO/RTO и проверить восстановление. Расписание backups зависит от допустимой потери данных, а не от произвольной красивой цифры.
- Контролировать память, CPU, соединения, объём БД, storage, трафик и стоимость. Установить квоты и уведомления о росте.
- CDN использовать для публичной статики. Не кэшировать документы и сессии как публичные ресурсы.
- Не держать постоянно работающий OCR/AI worker без измеримой потребности; для этапа 1 выбрать запуск по требованию или ограниченную конкурентность с предсказуемой стоимостью.

## 14. Фоновые задачи и дальнейшее масштабирование

- Worker добавлять при первом действительно долгом задании; очередь должна переживать рестарт.
- Первый вариант — очередь на PostgreSQL, например pg-boss после проверки совместимости: позволяет начать без Redis.
- Задания имеют tenant, статус, лимит попыток, backoff, таймаут, блокировку/lease и защиту от повторного выполнения.
- Считать доставку как минимум повторяемой, делать обработчики идемпотентными; не обещать exactly-once.
- Для связки записи в БД и постановки задания использовать общую транзакцию, если поддерживается, или outbox.
- Конкурентность ограничивать по памяти и компании, чтобы одна большая загрузка не блокировала остальных.
- OCR/AI этапа 1 выносить из HTTP-пути, если обработка долгая; всегда предусматривать происхождение результатов, ручное подтверждение и лимиты стоимости.
- Redis, отдельные API-реплики и разделение сервисов добавлять по профилю нагрузки. Перед несколькими репликами решить общие лимиты, кэш, фоновые задания и согласованность конфигурации.

## 15. Требования к производительности

Это целевые бюджеты для измерения, не утверждение о нынешнем прототипе:

- Публичные страницы: LCP ≤ 2,5 с, INP ≤ 200 мс, CLS ≤ 0,1 на 75-м перцентиле реальных посещений; до появления трафика — воспроизводимый лабораторный профиль.
- Для публичной страницы стартовый бюджет загружаемого JS до 200 KiB gzip, включая framework chunks. Превышение требует анализа bundle и записанного обоснования.
- Обычные операции списка/карточки: целевой p95 серверной обработки до 500 мс при согласованной тестовой нагрузке. Загрузка файлов и большие экспорты измеряются отдельно.
- Проверять production build: размер клиентских chunks, память процесса, запросы БД и задержки. Маленький bundle не означает автоматически низкую нагрузку сервера.
- Не загружать документы, редакторы и тяжёлые таблицы в код публичной страницы. Использовать разделение маршрутов и динамическую загрузку там, где это нужно.
- Не делать постоянный polling для неизменяющихся данных. Не отдавать тысячи строк, когда видна одна страница.
- Оптимизации подтверждать сравнением до/после. Не добавлять memo, кэш и новый сервис без измеримого эффекта или ясной причины.

## 16. Проверки, релизы и документация

При создании приложения настроить реальные scripts: dev, build, start, lint, typecheck, format:check, test, test:integration, test:e2e и отдельные команды миграций. Сейчас наличие этих команд не предполагается.

- CI: frozen install → lint/typecheck → подходящие tests → production build. Запускать Prettier check; не заменять смысловые проверки форматированием.
- Unit: преобразования данных, правила карты готовности, валидация, разрешения и экранирование форматов выдачи.
- Integration на PostgreSQL: tenant isolation, транзакции, миграции, отзыв API-ключей, права на экспорт/файлы.
- E2E этапа 1: регистрация/вход, организация, загрузка документов, AI-извлечение на контролируемых фикстурах, отображение источников и пропусков, ручное подтверждение, структурированный результат, RU/EN и обе темы.
- Обязательно отрицательные сценарии: другой tenant, отсутствующие права, чужой документ, неверный ключ, повторное задание и превышение квоты.
- Проверять с чистой базой и обновлением схемы предыдущего релиза. В тестах не использовать реальные клиентские документы.
- Отдельно проверять клавиатуру, фокус, 320 px, масштабирование, контраст реальной пары на конкретной поверхности. Наличие HEX в брендбуке не доказывает доступность.
- Релиз имеет healthcheck, наблюдаемость и план rollback приложения с учётом совместимости БД.
- Логи структурированные: requestId, безопасный идентификатор компании, статус, длительность. Ошибки и slow queries наблюдаемы; содержимое файлов и секреты исключены.
- Крупные архитектурные изменения фиксировать коротким ADR в docs/architecture: проблема, решение, альтернативы, влияние на стоимость и переносимость.
- Документировать фактическую настройку окружения, запуск, migrations, backups/restore, API и deployment в README/docs.
- По завершении задачи сообщать, что сделано и что реально проверено. Не заявлять визуальные, нагрузочные или security-проверки без выполнения.
